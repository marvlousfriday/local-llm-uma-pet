# 01 · 本地大模型：Qwen3.5-9B on 8GB VRAM

> 目标：在一张 8GB 显卡上，跑一个能日常聊天、能看图、上下文够长的中文模型，并且**不爆显存**。
>
> 测试环境：RTX 3060 Ti 8GB / 驱动 617.14 / Ollama 0.40.14。本文所有数字均为实测。

---

## 结论先行

选 **Qwen3.5-9B (Q4_K_M)**，不选 27B、不选 14B。理由很简单：

| 候选 | Q4 权重大小 | 8GB 卡 |
|---|---|---|
| 27B | ≈16 GB | 必爆，除非大量 offload 到 CPU（速度掉到个位数） |
| 14B | ≈9 GB | 勉强，KV cache 一开就溢出 |
| **9B** | **6.6 GB** | **权重 5.24GB + 视觉塔 0.86GB = 6.10GB 固定开销，剩余够 16K 上下文** |

顺带纠正一个常见误区：**别为了显存去买 4060 Ti 16GB**。它的显存带宽 288GB/s，低于 3060 Ti 的 448GB/s，推理反而更慢。真要上大模型，一步到位 3090（24GB / 936GB/s）。

---

## 实测性能

| 模型 | 上下文 | 显存占用 | 计算位置 | 生成速度 |
|---|---|---|---|---|
| `qwen9b` | 16K | **7749 MiB** | 100% GPU | **63 tok/s** |
| `qwen9b32k` | 32K | **7851 MiB** | 100% GPU | 48 tok/s |
| （对照）| 8K | 7715 MiB | 100% GPU | 62 tok/s |

- 首次加载约 45 秒（磁盘读 6.6GB），之后模型驻留显存，二次加载约 10 秒
- 32K 比 16K 慢约 25%，是 attention 计算量变大的正常代价，不是配置问题
- **32K 只剩约 340MB 余量**：浏览器开硬件加速、剪辑软件、游戏同时开，模型会被挤出到 CPU，速度掉到个位数

所以：**日常用 16K，读长文档才切 32K**。340MB 的余量不足以支撑"边跑模型边开一堆程序"。

省显存的两项关键配置（原方案没提，是 32K 能塞下的真正原因）：

```bash
OLLAMA_FLASH_ATTENTION=1     # FlashAttention，省 attention 中间张量
OLLAMA_KV_CACHE_TYPE=q8_0    # KV cache 从 f16 量化到 q8_0，约省 0.4GB
```

`install.bat` 已自动写入这两项。

## 快速部署

```bat
cd llm
install.bat
```

脚本做四件事：

1. 检测 Ollama，没有就用 `winget` 装（装不上会提示手动下载地址）
2. 写入四个环境变量（见上 + `NUM_PARALLEL=1` + `MAX_LOADED_MODELS=1`）
3. `ollama pull qwen3.5:9b`（6.1GB，视网速 5–30 分钟，中断可续传）
4. 用 `Modelfile` 生成 `qwen9b`，再把 `num_ctx` 替换成 32768 生成 `qwen9b32k`

`Modelfile` 的全部参数：

```
FROM qwen3.5:9b
PARAMETER num_ctx 16384     # 显存主要开销，不是 num_predict
PARAMETER num_gpu 99        # 全部层交给 GPU，不够时 ollama 自动溢出
PARAMETER num_predict 2048  # 单次生成闸门，防思考链跑飞
PARAMETER temperature 0.7
PARAMETER top_p 0.8
PARAMETER top_k 20
PARAMETER min_p 0.0
PARAMETER repeat_penalty 1.05
```

采样参数用的是 Qwen3.5 官方推荐的非思考场景配置，别随意调 `top_p`/`temperature`，调了容易开始胡说。

## 为什么模型答不出日期

这是本地模型最容易让人怀疑"是不是装坏了"的地方。

**本地模型没有时钟。** 训练数据有截止时间，它不知道今天几号——这不是 bug，是必然。它会在思考链里反复自我怀疑，把 `num_predict` 烧光，最后 `done_reason: length`，回答是空的。

同一句"今天是几号"的对比：

| 方式 | 生成 token | 耗时 | 结果 |
|---|---|---|---|
| `ollama run qwen9b` | 2023 | 32 秒 | 勉强给出答案，随时可能被上限截断 |
| `ask.bat`（注入系统日期 + 关思考） | 19 | **0.3 秒** | 正确回答「2026年11月3日 星期二」 |

`ask.ps1` 的做法：把 `Get-Date` 的结果写进 system 提示，并显式告诉模型"涉及日期一律以此为准"，同时 `think: false`。

凡是需要外部信息的问题都有同样的毛病：今天天气、最新版本号、当前股价、某人现任职务。**要么把事实写进提示词，要么关掉思考让它直接编——然后别信。**

## 思考模式

Qwen3.5 默认开启思考链（`think: true`），生成的 token 先花在思考上。实测给 80 token 上限时，token 全被思考吃掉，**回答是空的**。

三种处理方式：

1. **API 调用关掉**（最干净，`ask.ps1` 和 `OllamaClient.cs` 都用这个）：

```bash
curl http://127.0.0.1:11434/api/generate -d '{"model":"qwen9b","prompt":"你好","think":false}'
```

2. **CLI 只是不显示**：`ollama run qwen9b --hidethinking` —— token 照样消耗，别指望它省时间
3. **保留思考但别被截断**：`Modelfile` 里 `num_predict` 已设 2048

### 关思考会不会变笨（四道题实测）

| 题目 | 关思考 | 开思考 | 正确性 |
|---|---|---|---|
| 鸡兔同笼 | 98 token / 10.5s | 1732 token / 27.0s | 都对 |
| 代码 bug 分析 | 376 token / 6.0s | 1976 token / 31.1s | 都对 |
| 中译英 | 67 token / 1.2s | 1097 token / 17.2s | 都对 |
| 12 球称重（难题） | 2048 token / 32.4s，**被截断** | 1388 token / 21.7s，完整 | 关思考未完成 |

结论：

- **简单任务**：关思考几乎无损失，快 3–17 倍
- **难题**：思考模式反而更省——推导放在思考区不进正文，不容易撞 `num_predict`
- **风险点**：关思考时模型把推导全写进正文，长答案更容易被截断

**建议**：日常关，遇到推理/数学/复杂代码再开。判断方法很土但有效——关思考给的答案如果含糊，重开思考问一遍。

## num_predict 怎么调

它只是"最多生成多少 token"的闸门，**不占显存**（显存由 `num_ctx` 决定）。改大的代价只有时间和上下文占用。

实测约束（2K 上下文 + 4K 输出上限）：

```
输入 39 token + 生成 2009 token = 2048 → 顶满 num_ctx
done_reason: length，没有报错，安静截断
```

所以**真正管输出上限的是 `num_ctx - 输入 token`**，`num_predict` 只是提前刹车。

| 场景 | 建议值 |
|---|---|
| 日常问答 | 512–1024 |
| 写文章 / 长代码 | 2048–4096（`num_ctx` 需同步够大） |
| `-1` | 不推荐，一直生成到上下文满 |

16K 上下文理论输出上限约 16000 token，但 60 tok/s 下要等 **4 分半**。指望调大 `num_predict` 解决"答不出日期"没用——它只会多绕几倍时间，给出同样那句"我无法确定"。

改法：编辑 `Modelfile` 的 `PARAMETER num_predict`，然后 `ollama create qwen9b -f Modelfile` 重建。

## 多模态：能看图

Qwen3.5 是原生视觉语言模型（`Qwen3_5ForConditionalGeneration`），模型包自带 0.86GB 视觉塔——**不需要另装 VL 模型**。

```bash
ollama run qwen9b "这张图里有什么？" < 图片路径.jpg
```

代价是那 0.86GB 常驻显存，如果你的卡只有 6GB，这 0.86GB 就是压垮骆驼的那根稻草。

## 怎么关（三层，别只做第一层）

| 你做的操作 | 对话界面 | 显存 | 服务 |
|---|---|---|---|
| `/bye` 或 `Ctrl+D` | 关 | **仍占用 5 分钟** | 运行 |
| `ollama stop qwen9b` | 无影响 | 立即释放 | 运行 |
| 托盘 Quit / `taskkill` | 关 | 释放 | 停止 |

- **第 1 层**：`/bye`。注意 `Ctrl+C` 只中断当前生成，不退出也不卸载
- **第 2 层**：`ollama stop qwen9b`。实测 7619 MiB → 994 MiB，服务仍在监听。想用完即释放：`--keepalive 0`
- **第 3 层**：托盘右键 Quit，或 `taskkill /F /IM "ollama app.exe"` + `taskkill /F /IM ollama.exe`

服务本身只占约 50MB，显存不够时**只需要第 2 层**，不用关服务。

## 起不来怎么办

不需要每次手动 `ollama serve`。三条路径都会自动带起服务：登录自启的托盘 `Ollama.lnk`、`ollama run` 自动拉起、开始菜单点一下。

只有两种情况需要手动：

- 托盘进程僵死（`ollama app.exe` 在但 11434 没监听）
- 无桌面会话（远程 SSH、计划任务、自动化脚本）——此时启动 GUI 版会报 `timeout waiting for Ollama server to be ready`，**不是坏了，是拿不到桌面上下文**，改用 `ollama serve` 命令行版

自查：

```bash
curl http://127.0.0.1:11434/api/version    # 返回版本号 = 活着
```

或者双击 `check-params.bat`，一次输出四件事：用户环境变量、服务状态、已加载模型、模型进程实际参数（KV 是否 q8_0 / FA 是否开 / 上下文长度 / GPU 层数）。

> **托盘版和命令行版读同一套环境变量**，效果完全一样。唯一前提：变量必须在服务进程启动前已存在。
> 若 `check-params.bat` 显示「KV cache: 未量化」，说明托盘进程读的是旧环境——退出 Ollama 再启动一次。

排查顺序：任务管理器结束 `ollama app.exe` → 开始菜单重开 → 还不行就开终端跑 `ollama serve` 看报错原文。

## 维护

```bash
ollama list                 # 看已装模型
ollama ps                   # 看当前在 GPU 还是 CPU、占多少上下文
ollama rm qwen9b32k         # 删模型（省 6.6GB 磁盘）
ollama cp qwen9b 我的助手    # 复制一份改着玩
```

### 模型文件挪出 C 盘

模型默认落在 `%USERPROFILE%\.ollama\models`，6.6GB 对 C 盘很肉疼。

```bash
setx OLLAMA_MODELS "<自定义目录>\ollama\models"
# 把 .ollama\models 整个挪过去，重启 Ollama
```

三个模型共享同一份 blob，实际占用约 6.2GB 而非 19.8GB。

## 接入其它前端

Open WebUI / AnythingLLM / Chatbox 等：地址填 `http://127.0.0.1:11434`，模型选 `qwen9b`。

> 如果前端报 502 或连接失败，先看系统有没有设 `HTTP_PROXY`。Clash 之类的会把 `127.0.0.1` 也代理掉，需要在 `NO_PROXY` 里加 `127.0.0.1,localhost`。详见 [03](03-桌宠集成.md#坑-2系统代理劫持本地请求)。
