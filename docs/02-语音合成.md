# 02 · 语音合成：VITS 马娘音色 → HTTP 服务

> 目标：把 [UmaChat_WebApi](https://github.com/kagari-bi/UmaChat_WebApi) 的 VITS 推理包成桌宠能直接调的 HTTP 接口，**跑在 CPU 上，不跟大模型抢显存**。

---

## 为什么自己包一层

UmaChat_WebApi 原本是个带 Web UI 的 Flask 应用，直接给桌宠用有三个问题：

1. 依赖 Flask + 一堆前端资源，桌面端不需要
2. 没有生命周期管理——桌宠退出后进程留在后台占着端口和内存
3. 常驻内存 786MB，而桌宠可能一整天没人理

所以换成了 200 行的标准库 `ThreadingHTTPServer`，加两个自研机制：**父进程守卫**和**空闲卸载**。

---

## 接口

```http
POST /tts
Content-Type: application/json

{"text": "こんにちは、今日も元気だね", "speed": 1.0}
```

响应：`audio/wav` 字节流，附 `X-Sample-Rate` / `X-Duration` 头。

```http
GET /health
→ {"ok":true,"model":"MeishoDoto","loaded":true,"idle_timeout":600,
   "idle_seconds":12.3,"sampling_rate":22050}
```

`loaded` 和 `idle_seconds` 是排查用的——能直接看出模型是被卸载了还是单纯慢。


> **注意是 `pyopenjtalk-plus` 不是 `pyopenjtalk`**。后者官方只有源码包，Windows 上要 MSVC 编译，十有八九失败；`-plus` 有 cp311 轮子，模块名不变，`import pyopenjtalk` 照常。

```bat

```

参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--port` | 9880 | |
| `--char` | MeishoDoto | 对应 `models/<角色名>/` |

## 性能

CPU 推理，RTF 约 **0.33**（生成 1 秒音频耗时 0.33 秒，比实时快 3 倍）。一句 15 字的日语约 1.2 秒出音频。

不占显存是刻意的设计——8GB 卡上 `qwen9b` 已经吃掉 7.7GB，再塞一个语音模型必然溢出到 CPU，两边一起卡。

空闲卸载实测：

| 状态 | 内存 |
|---|---|
| 模型常驻 | 786 MB |
| 空闲 600s 后 | **8.8 MB** |
| 重载耗时 | 0.4 s（端到端 1.2 s） |

## 坑 1：音素序列长度为 1

最隐蔽的一个。现象是服务不报错，返回的 wav 只有几十毫秒的静音。

原因：模型用的是 `zh_ja_mixture_cleaners`，这个 cleaner **只处理 `[JA]` 标记内的文本**。你直接把纯日语 `こんにちは` 丢进 `text_to_sequence(text, hps.symbols, ["zh_ja_mixture_cleaners"])`，没有 `[JA]` 标记 → 全被丢弃 → 序列只剩标点 → 长度 1。

解法是绕开 cleaner，自己先转罗马音：

```python
romaji = japanese_to_romaji_with_accent(text)      # こんにちは → konnichiwa
romaji = romaji.replace("ts", "ʦ").replace("u", "ɯ").replace("...", "…")
seq = text_to_sequence(romaji, _HPS.symbols, [])    # 第三个参数传空列表，不做清理
```

`_HPS.symbols` 也必须显式传——不传的话 `text_to_sequence` 会用默认符号表，音素 id 对不上，输出是乱码音频。

## 坑 2：EmptyWorkingSet 静默失败

日志明明打印了"已释放"，任务管理器里内存纹丝不动。

```python
# 错误写法
k32.GetCurrentProcess()          # 返回 -1 伪句柄，ctypes 默认按 c_int 截断成 32 位
psapi.EmptyWorkingSet(-1)        # 静默失败
```

`GetCurrentProcess()` 返回的是伪句柄 `-1`（`0xFFFFFFFFFFFFFFFF`），ctypes 默认 `restype` 是 `c_int`，64 位句柄被截成 `0xFFFFFFFF`，`EmptyWorkingSet` 收到无效句柄直接返回 False，而代码没检查返回值。

正确写法：

```python
k32.GetCurrentProcess.restype = ctypes.c_void_p
psapi.EmptyWorkingSet.argtypes = [ctypes.c_void_p]
psapi.EmptyWorkingSet.restype = ctypes.c_bool
ok = psapi.EmptyWorkingSet(k32.GetCurrentProcess())
```

另外 `gc.collect()` 只回收 Python 对象，**torch 的 C++ 内存池不会还给系统**。真正让 RSS 掉下来的是 `EmptyWorkingSet`（把工作集刷到页面文件），不是 gc。

---

## 坑 3：孤儿进程

`venv/Scripts/pythonw.exe` 只是个启动器，真正的解释器是它 fork 出来的子进程。直接 `Process.Kill()` 杀掉启动器，解释器活着继续占 9880 端口，下次启动直接端口冲突。

三重保障：

1. **正常退出** → `App.Exit` 里 `taskkill /PID xxx /T /F`（`/T` 连进程树）
2. **强杀 / 崩溃**（不走 Exit 事件）→ 启动时传 `--parent-pid <桌宠PID>`，服务每 5 秒 `OpenProcess` + `GetExitCodeProcess` 查一次（`STILL_ACTIVE = 259`），父进程没了就 `os._exit(0)`
3. **万一还漏** → 空闲卸载把内存压到 8.8MB，不占资源

第 2 条不是可选优化：`Stop-Process -Force`、任务管理器结束、进程崩溃**都不会触发 `Application.Exit`**，只靠第 1 条必然留孤儿。

`pid_alive()` 里查不到就 `return True`——宁可漏杀也不能误杀，因为 PID 会被复用，一个错误的 `os._exit` 会让正常服务莫名其妙消失。

---

## 坑 4：pythonw 下 print 即崩溃

`pythonw.exe` 没有控制台，`sys.stdout` / `sys.stderr` 是 `None`。任何 `print()` 都会 `AttributeError: 'NoneType' object has no attribute 'write'`，进程当场死掉，而且**没有任何提示**——用户只看到"桌宠不出声"。

服务开头必须先兜住：

```python
if sys.stdout is None or sys.stderr is None:
    _f = open(os.path.join(BASE, "tts_server.log"), "a", encoding="utf-8", buffering=1)
    if sys.stdout is None: sys.stdout = _f
    if sys.stderr is None: sys.stderr = _f
```

顺手解决了日志问题——桌宠后台拉起服务时，出问题唯一能查的就是这个文件。

---

## 推理串行化

`ThreadingHTTPServer` 是多线程的，但 torch 模型和 `_NET`/`_HPS` 这两个全局变量不是线程安全的。两个请求同时进来会互相踩，输出音频错乱甚至崩溃。

用一把 `_LOCK` 把推理串起来，同时保护 `unload_model`：

```python
with _LOCK:
    with torch.no_grad():
        audio = _NET.infer(...)
```

空闲看门狗在卸载前也检查 `_LOCK.locked()`——正在推理时绝不卸载。

对桌宠场景来说串行无所谓：一次只念一句。

## 换音色

改 `--char`，对应下载 `models/<角色名>/`。

```bat
venv\Scripts\pythonw.exe tts_server.py --char SpecialWeek
```

可用角色见 [gouhuo/Umamusume_Vits_models](https://huggingface.co/gouhuo/Umamusume_Vits_models) 的目录列表。
